# Traduction (i18n)

- **Langues** : `fr` (défaut), `en`, `br` (breton). Config dans `config/packages/translation.yaml` (`default_locale: fr`, `enabled_locales: [fr, en, br]`, `fallbacks: [fr]`).
- **Fichiers** : `translations/messages.{fr,en,br}.yaml` (templates Twig + labels/placeholders de formulaires) et `translations/validators.{fr,en,br}.yaml` (messages de contrainte de validation, cf. Gotcha ci-dessous).
- **Sélecteur de langue** : 3 liens `FR`/`EN`/`BR` dans `templates/partials/header.html.twig` (public, refait en liens simples lors de la refonte de la navbar : un `<select class="form-control">` mélangeait le chrome par défaut de Bootstrap avec le style custom). Toujours un `<select onchange="window.location.href=this.value">` dans `templates/desk/partials/header.html.twig` (espace membre), pas retouché. Les deux pointent vers `/locale/{locale}`.
- **Changement de locale** : route `app_locale` (`src/Controller/LocaleController.php`), stocke `_locale` en session puis redirige vers le `referer` (fallback `home` si absent ou externe). `src/EventSubscriber/LocaleSubscriber.php` relit `_locale` depuis la session sur chaque requête (`kernel.request`, priorité 20) et l'applique à `Request::setLocale()`.

## Comment une clé de traduction est résolue

- **Dans les templates Twig** : `{{ 'ma.cle'|trans }}` (domaine `messages` par défaut). Pour interpoler une variable : `{{ 'desk.hello'|trans({'%nickname%': app.user.nickname}) }}` avec `%nickname%` dans la chaîne de traduction.
- **Dans les formulaires (`src/Form/*.php`)** : les `label` (y compris ceux passés directement dans `->add(...)`, pas seulement via `getConfiguration()`) et les clés de `choices` sont traduits **automatiquement** par le thème de formulaire Symfony, tant qu'une entrée existe dans `messages.*.yaml` avec le texte du label comme id. Les `attr.placeholder`, eux, ne sont **pas** traduits automatiquement (pas gérés par le moteur de formulaire) : `ApplicationType::getConfiguration()` (parente de la plupart des `Form/*Type.php`) injecte `TranslatorInterface` et traduit explicitement `label` et `placeholder` avant de les passer à `->add()`.
- **Messages de contrainte de validation** (`new File(['mimeTypesMessage' => '...'])`, etc.) : Symfony les traduit automatiquement dans le domaine **`validators`** (pas `messages`), en utilisant le texte du message comme id. C'est pour ça que ces chaînes ont leur propre fichier `validators.*.yaml` plutôt que `messages.*.yaml`.
- Convention de clé : namespacée en dot-notation (`nav.home`, `story.who_title`...) pour le texte propre aux templates, mais id = **texte source littéral** (celui déjà en dur dans le code) pour tout ce qui passe par un label de formulaire ou un message de contrainte, puisque c'est ce texte-là que Symfony utilise comme id de recherche.

## Ajouter une nouvelle clé

1. Twig : remplacer le texte en dur par `{{ 'domaine.cle'|trans }}`, ajouter l'entrée dans les 3 fichiers `messages.{fr,en,br}.yaml`.
2. Formulaire : passer par `getConfiguration($label, $placeholder)` si le `Form\*Type` en hérite (traduction automatique), sinon ajouter l'entrée dans `messages.*.yaml` avec le texte littéral du `label` comme id.
3. Lancer `php bin/console debug:translation fr --only-missing` (et `en`) pour vérifier qu'aucune clé n'est oubliée. `br` n'est **pas** vérifié par ce check (voir Gotcha).

## Gotcha

- **Le check CI (`lint-php-twig`) n'inclut pas `br` dans le contrôle strict `--only-missing`.** Symfony embarque ses propres traductions internes (messages de validation/sécurité du framework) en français et en anglais, mais évidemment pas en breton : `debug:translation br --only-missing` remonterait donc en permanence du bruit venant du framework lui-même, pas de vraies clés manquantes côté app. Le lint YAML (`lint:yaml translations/`) reste appliqué à `br`.
- **Traduction breton non relue par un·e locuteur·rice native.** C'est une base "pour le fun" (cf. ROADMAP Phase 4), pas une traduction professionnelle : à faire vérifier si l'exactitude devient importante un jour.
- Les commandes `bin/console` (dont `debug:translation`) ont besoin d'un fichier `.env` pour démarrer le kernel (`config/bootstrap.php`), ce que la CI n'a pas par défaut : le job `lint-php-twig` en crée un éphémère juste avant ce step (`APP_ENV=test` + une `DATABASE_URL` factice, jamais commités). Sans la `DATABASE_URL`, le kernel refuse de booter (`EnvVarProcessor`) même si la commande ne touche jamais la base : bug passé inaperçu 4 jours après le retrait de `.env` du tracking git, corrigé le 2026-08-10.
